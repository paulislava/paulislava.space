Apache слушает `127.0.0.1:8080` и `127.0.0.1:8445`. Hestia слушает `127.0.0.1:8083` и доступна администратору через SSH-туннель. Публичный HTTP для `panel.paulislava.space` возвращает 404.

В закрытом каталоге `/root/hestia-migration-20261125/source/` сохранены исходные пользовательские записи Hestia, сайты и шаблоны из `E:\backup`. Для действующих сайтов Hestia обновлены IP, upstream и сертификаты. Архивные настройки DNS, почты и VPN хранятся там же. UrFU1 сохранён в статусе suspended.

Резервный SSH домашнего хаба идёт напрямую на production VPS `45.9.41.107`. Пользовательская служба `tv-home-ssh-recovery.service` на хабе подключается выделенным ключом. SSH на VPS разрешает этой учётной записи только обратный порт `127.0.0.1:21666`. Для входа используй `ssh -o HostKeyAlias=192.168.0.100 -J prod -p 21666 paulislava@127.0.0.1`. Проверены повторный вход после перезапуска службы на хабе и отказ перенаправления на другой порт. Прежняя служба `tv-frpc.service` остановлена, её конфигурация сохранена на хабе.

Резервный вход на Windows-ПК с Mac — `ssh pc-remote`. Алиас проходит через `prod` на `127.0.0.1:25000` с проверкой прежнего ключа хоста Windows. На ПК служба `PcRemoteProdSSH` автоматически поднимает туннель к `prod` под LocalSystem. SSH-учётная запись `pc-ssh-relay` на VPS разрешает только обратное перенаправление этого loopback-порта. Вход проверен после перезапуска службы и отключения `PcRemoteFRP`. Порт на прежнем VPN-сервере закрыт. Для обслуживания Windows используется LAN-алиас `ssh pc`.

WireGuard-мост `tvsite` соединяет домашнюю сеть `192.168.0.0/24` и квартирную `192.168.1.0/24` через `prod`. Квартирный роутер подключается к UDP/51830, домашний — к UDP/443 с перенаправлением на UDP/51830. На VPS включены `wg-quick@tvsite.service` и `tvsite-firewall.service`. Hestia повторно добавляет нужные правила через `custom.sh`. На обоих роутерах резерв конфигурации находится в `/root/tvsite-network-before-prod-20261125`. Проверены оба handshake, пинг между подсетями и SSH с Mac на домашний роутер и хаб.

Окончательный PostgreSQL-дамп CMS снят с действующей базы Windows после остановки старой CMS и проверен по SHA-256. Восстановлено 103 таблицы. База TV и Redis также взяты с действующего сервиса на ПК. Beznomera, NoSmoke и PaulIsMapa восстановлены из логических дампов, извлечённых из изолированной копии PostgreSQL в `E:\backup`. Старая CMS в Windows остановлена и переведена на ручной запуск. Прежние маршруты nginx для CMS, Web, Proff и Водомера ведут на новый VPS с проверкой TLS, пока клиенты используют прежний DNS.

## SiestaNet API

SiestaNet API работает на `prod` под `vpn-access.service`. Контейнер `siestanet-api` слушает `127.0.0.1:19402`. На VPN-сервере nginx направляет API основного адреса `net.beznomera.net` и обоих зеркал через закрытый SSH-туннель `siesta-api-vpn-relay.service` на loopback-порт `14022`. Все три публичных входа вернули одинаковую ревизию учётных данных при авторизованном запросе. Четыре службы сверки VPN подтвердили связь с новым API.

Прямой резерв API на `prod` — `https://paulislava.space:8444`. Подписанный список версии 4 заменил недоступный адрес старого VPS. У основного адреса, прямого резерва и зеркал совпадают подписанные конфигурации. Резервный маршрут регистрации использует существующую службу ПК через проверенный HTTPS на VPN-сервере.

Актуальная база `vpn_access` перенесена из Windows в основной PostgreSQL 18 на `prod`. Совпали SHA-256 финального дампа и количество строк во всех 19 таблицах. Обе службы регистрации остались на ПК и используют эту же базу через `SiestaNetProdTunnel`. Через него `prod` получает опубликованные реестры Level 3 с ПК. Обычный и AI-реестры побайтно совпали с источником. Публичное чтение статуса регистрации, загрузки и создание резервной копии под Windows LocalService проверены.

На ПК остановлены и выключены из автозапуска `PaulislavaCMSFRP`, `PaulislavaWebFRP`, `PaulislavaProffFRP`, `VodomerUralFRP`, `SiestaNetAPI` и `SiestaNetFRP`. На VPN закрыты соответствующие порты `24002`, `24005`, `24006`, `24008` и `24009`. `SiestaNetDeviceRegistrationFRP` и `SiestaNetDownloadsFRP` продолжают работать на `24003` и `24004`.

Для отката API сначала остановить `vpn-access.service` на `prod`. Затем временно включить Windows API и его FRP с текущим `.runtime/env`, который указывает на PostgreSQL `prod`. Проверить API через `24002` и восстановить три маршрута nginx из `/root/siestanet-api-ingress.YPiozsxU` на VPN-сервере. Исходная база Windows сохранена как снимок до переключения.

Команда `siestanet-issue-code` на Mac использует SSH-алиас `prod`. Проверено чтение статуса действующего кода. Операция `user set-ai-proxy` останавливается до записи в базу, поскольку служба синхронизации маршрутов AI отсутствует на обоих VPS.

## S3 и ежедневные резервные копии

Производственный S3 — `https://s3.ru1.storage.beget.cloud`, регион `ru1`, bucket `4565b9a17706-paulislava-s3`, path-style. Публичные ссылки сохраняются через `https://cdn.paulislava.space/<key>` и совместимый путь `/paulislava-media/<key>`. Nginx разрешает чтение объектов и проверяет TLS Beget S3. Сертификат CDN обслуживает Certbot. Проверка пробного продления завершилась успешно.

Все 86 объектов из RustFS скопированы с сохранением ключей. После остановки старой CMS повторная проверка скачанного содержимого подтвердила 86 совпадений и 0 расхождений. RustFS остаётся на ПК в `E:\Services\PaulislavaS3`, bucket `paulislava-media`. На ПК endpoint `http://127.0.0.1:19000`, в LAN `http://192.168.1.200:19000`. На квартирном роутере DHCP закрепляет за ПК `192.168.1.200`. `pc`, `pc.lan` и `pc.local` разрешаются в этот адрес. SSH-алиас `pc` входит на ПК через квартирный роутер.

На Mac новые запуски MCP `aws-s3` используют production S3 Beget, а `aws-s3-local` по-прежнему использует RustFS по LAN. У Beget отдельный файл credentials с правами `0600`. Для имени `s3.ru1.storage.beget.cloud` launcher использует отдельный DNS-резолвер, поскольку системный резолвер Mac возвращал адрес, на котором HTTPS не отвечал. TLS проверяется по имени Beget. MCP `list_objects` проверен на известном ключе в обоих бакетах.

| Задача Windows | Что сохраняет |
| --- | --- |
| `PaulislavaS3ProdToReserve` | Передаёт в RustFS отсутствующие и изменившиеся объекты. Сравнивает размер и общий MD5. Если общего MD5 нет, сравнивает потоковый SHA-256. Объекты, которые есть только в резерве, сохраняются |
| `PaulislavaPostgresProdBackup` | Загружает все базы, допускающие подключение, и глобальные объекты основного PostgreSQL 18. Проверяет архив по SHA-256. После успешной проверки хранит архивы за сегодня и вчера в `E:\Services\PaulislavaPostgresBackup\archives` |

Обе задачи стартуют ежедневно в 04:00 по Екатеринбургу. Первый ручной и первый плановый запуски завершились с кодом 0. Плановый архив от 25 ноября содержит 11 баз, включая `vpn_access`. Из более раннего архива на ПК в отдельном PostgreSQL успешно восстановлены все десять баз, включая `paulislava_cms` (103 таблицы) и `tv_service` (69 таблиц), а также глобальные объекты. После проверки временный кластер остановлен. Сценарий S3 проверен на обычных и multipart-объектах, в том числе при изменении содержимого без изменения размера.

SSH-ключ PostgreSQL разрешает только выполнение `/usr/local/sbin/pc-postgres-backup`. Ключ S3 и служебные конфигурации хранятся вне Git. Исходный `E:\backup` сохранён.

## Учётные записи и GitHub Actions

Хэши паролей `root`, `bridge`, `admin`, `oleg` и `user` совпадают со снимком. Все исходные SSH-ключи сохранены. Вход по SSH за `root` и `admin` проверен. Для `oleg` сверены четыре ключа, соответствующего приватного ключа на Mac нет. Для `bridge` действует прежний вход только по ключу, для `user` сохранён SFTP chroot. В Hestia восстановлены роли `admin`, `oleg` и `user`. `hestiaadmin` остаётся основным администратором. `admin` и `oleg` получили новые UID. Прежние права `sudo` и `docker` не перенесены. `user_pos` сохранён в заблокированном состоянии, FTP выключен. В WordPress и Mentorial совпали учётные записи и хэши паролей.

Linux-раннер NoSmoke `nosmoke-production` подключён с метками `self-hosted`, `Linux` и `X64`. Раннер `macbook-paul` также доступен. Beznomera `PaulIsLava` подключён с меткой `migration-hold-20261125`. В открытом PR остался старый workflow с Docker-командами на `self-hosted`, поэтому Linux-раннер пока не принимает такие задания. Раннеры на VPS работают под разными учётными записями без доступа к Docker socket и production-секретам. GitHub подтвердил подключение. Задания и деплой для проверки не запускались.

Для Budget требуется новая регистрация раннера через администратора репозитория. При проверке сохранённой регистрации `my-budget-runner` GitHub ответил, что она удалена. Проверочный процесс остановлен, production job не запускалась. У текущей учётной записи есть доступ на запись, API раннеров возвращает 404. У Human4AI self-hosted runner отсутствует, прежний deploy workflow отключён вручную.

## Ограничения

- Posurfu отвечает по HTTPS на новом IP. Домен отсутствует в доступном аккаунте Beget, публичной A-записи нет.
- В доступной MariaDB-копии исходной `user_proff.accounts` нет. На VPS создана пустая таблица по запросам PHP и локальная роль с `SELECT`, `INSERT` и `UPDATE` только для этой таблицы. PHP подключается, выборка выполняется, HTTP отвечает 200. Вход прежних пользователей требует восстановления записей. Для Proff отключены access logs, так как старые клиенты передают пароль в строке запроса.
- Beznomera API и Web отвечают, прежний S3 возвращает 403 на запрос существующего вложения. Вложения и связанные задания требуют доступа к исходному бакету.
- По решению Павла Budget обслуживается через VPN-сервер `13.143.194.252` и действующий FRP на отдельном ПК `gg7`. Публичный домен и upstream `127.0.0.1:24001` ответили HTTP 200.
- Старые вспомогательные маршруты без подтверждённого upstream сохранены в архиве Hestia.
